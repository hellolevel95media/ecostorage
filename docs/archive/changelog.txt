SECURITY — MUTATION TESTING FINDINGS (FIXED)
-----------------------------------------------
Ran adversarial/mutation tests against the API routes and rate limiter,
found and fixed 3 real vulnerabilities:

1. Rate limiter bypassable via X-Forwarded-For spoofing
   - src/lib/rate-limit.ts read the FIRST hop of X-Forwarded-For (client-
     controlled, trivially spoofable) instead of the LAST hop (the one the
     trusted edge/proxy actually appends). An attacker could rotate a fake IP
     per request and bypass rate limiting entirely.
   - Fixed: now keys off the last hop in the chain.

2. Unhandled exceptions returned bare empty 500 responses
   - /api/inquiries and /api/analytics called createServerSupabaseClient()
     without a try/catch; if it throws (e.g. missing/invalid Supabase env
     vars), the route crashed with an empty non-JSON body instead of a clean
     error, breaking the API contract for the frontend.
   - Fixed: wrapped both calls in try/catch with proper JSON error responses.

3. No request body size limit
   - Both POST routes fully parsed arbitrarily large payloads (tested up to
     5MB) before any validation ran — a low-cost DoS/amplification vector.
   - Fixed: added a Content-Length check (20KB cap) returning 413 before
     JSON parsing.

Verified via a 3-pass mutation test script (isolated-IP retest confirming
the bypass, then a clean 8/8 pass after fixes).

Known limitation, flagged not fixed: /admin/login's actual password check
runs client-side directly against Supabase's Auth API and never passes
through the rate-limiting middleware, so only the page load (not password-
guessing attempts) is currently throttled. Would require moving sign-in
behind a server route — a bigger architectural change, left as a decision
for later.

SECURITY — BEST PRACTICE HARDENING
-------------------------------------
- npm audit: 0 vulnerabilities across all 541 dependencies.
- next.config.ts: added `poweredByHeader: false` (drops the X-Powered-By
  fingerprinting header) and a Strict-Transport-Security header (defense in
  depth alongside whatever Vercel already adds).
- Confirmed no open-redirect vectors — all redirect() targets in the codebase
  are hardcoded literals, none user-controlled.
- RLS / admin access gap: every "admin" RLS policy in the DB grants access to
  ANY authenticated Supabase user, not specifically an admin — dangerous if
  Supabase's public sign-up is left enabled. Fixed with a fail-closed
  app-level email allowlist (ADMIN_ALLOWED_EMAILS env var) checked in
  src/app/admin/(protected)/layout.tsx — locks out everyone, including the
  real admin, until the env var is set. This is a BACKSTOP, not a
  replacement for disabling public sign-up in the Supabase dashboard (see
  todo.txt item 1 — still needs to be done by hand).
- Media uploads had no real size/type enforcement anywhere (client-side
  `accept` hint only, trivially bypassable). Fixed with a new migration
  (04_media_bucket_limits.sql) setting a real 50MB cap and an image/video
  MIME allowlist at the Supabase Storage bucket level (SVG deliberately
  excluded — embedded-script XSS risk on a publicly-served bucket), plus a
  matching client-side pre-check in MediaUploader.tsx for fast UX feedback.

LOAD-TIME / PERFORMANCE
--------------------------
- Found via production bundle analysis: the Supabase browser client
  (~67.5KB gzip) and the Sentry SDK (~126KB gzip) were both being eagerly
  loaded on every single page view, including the homepage, regardless of
  whether the visitor ever submitted a form or hit an error.
- Fixed: StorageCalculator.tsx now dynamically imports the Supabase client
  only inside its submit handler, instead of importing it at module scope.
  Confirmed via prod build that the chunk no longer appears in the
  homepage/personal-page HTML at all.
- Fixed: instrumentation-client.ts now only imports/initializes Sentry when
  NEXT_PUBLIC_SENTRY_DSN is actually set (it isn't yet — see todo.txt item
  4). Since that env var is inlined at build time, the whole Sentry import is
  dead-code-eliminated from the client bundle until Sentry is configured.
- Found and fixed a related latent bug while in there: the CSP's connect-src
  never allowlisted Sentry's ingest host, so once a real DSN is added, error
  reports would have been silently blocked by the site's own CSP. Now
  derives the ingest origin from the DSN automatically (same pattern already
  used for the Supabase host).
- Checked and confirmed fine, no changes needed: next/image config (not
  applicable yet — project deliberately uses no static images per its
  media-placeholder convention), font loading (already self-hosted via
  next/font/google, no external blocking requests).
